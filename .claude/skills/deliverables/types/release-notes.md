# Release notes

**Read by:** users deciding whether and how to upgrade.
**Inputs:** the changelog for the same cycle, the built user docs and the verification report.

The same content as the changelog, addressed to users: say what they can now do, not which files changed. Every entry still cites its source.

1. **Highlights** - the few changes users will notice most.
2. **Added** - new things users can do, from the changelog's added entries.
3. **Changed** - what behaves differently, from the changelog's changed entries.
4. **Removed** - what is gone and what to use instead.
5. **Fixed** - problems that no longer happen.
6. **Known issues** - open problems, with a workaround where the sources give one.
7. **Upgrade note** - the steps to upgrade, what to back up and what may break.
