# Brief: test writer for the in, not in, between and length card

## Objective and why

Project goal: a deterministic, no-eval template language for prompt assembly, with a headless core and an n8n node as a thin wrapper.
Cycle goal (`language`): authors can shape values, branch, loop, name, declare and reuse prompt fragments in the language itself without leaving the house style or the no-eval core.
Card goal: conditions test membership, ranges and sizes with `in`, `not in`, `between [a, b]` and `.length`; a quoted literal compares as text; an unrecognized word next to an operator is an error in every mode.
Your objective: turn each criterion into failing table-driven jest tests (`it.each` rows) in `tests/language/operators.test.ts` that fail for the right reason (an assertion, never a missing import or a syntax error), commit them, and record red evidence. The tests are the oracle the implementer is held to, so each must break on a plausible wrong implementation. Each test name starts with its criterion id (`op-in`, `op-between`, `op-length`, `op-equality`, `op-unknown`, `op-spec`).

- Edge rows the blind reviewer will probe (cover each):
  - op-in: array literal, array variable, quoted text, variable text; numbers vs text (n=1 with `n in ["1"]` is true because a quoted item compares as text and "1" equals "1"; `n in ["01"]` is false; `n in [1, 2]` numeric); empty list `[]`; missing and null left side (false for `in`, true for `not in`); a missing right side; list items that are variables; items holding commas, brackets and the words `and`, `in`, `not in` inside quotes; escaped quotes; duplicate and null elements; object and array elements never match; a right side that is a number, boolean or object is a type-error; a left side that is an array, object, cyclic object or BigInt is a type-error; an empty left text against a text right side is true; the substring test is case-sensitive; operator words in upper and mixed case (`IN`, `Not In`); malformed forms `x in [1,]`, `x in [,1]`, `x in [1 2]`, `x in [[1]]`, `x in [1`, `x in` are errors.
  - op-between: inclusive at both ends (the low, the high, just outside), numeric text operands, negative and decimal bounds, variable bounds, a low bound above the high bound is false; one bound or three bounds, a right side that is not a list, a non-numeric x, a null or missing x and a non-numeric bound are located type-errors in every mode; `not between` is not an operator (expect the Unrecognized condition error).
  - op-length: arrays, strings, empty array and empty string, astral text (`"😀"` is 2; `"a😀"` is 3), nested paths (`user.tags.length`, `items.0.length`), in IF conditions with a comparison and with `between`, in output `${{items.length}}`, in math `${{items.length + 1}}`, a CASE subject, a filter after it (`| upper` is harmless); an own key `length` on an object wins (values 7, null, 0, and a present key holding undefined, and a JSON object text holding `"length"`), an object without it gives empty output, a number or boolean has none; a missing array stays empty in output and `items.length > 0` on a missing array follows the existing ordering-operator rule (null is non-numeric, so it is the existing located type-error); a cyclic array still has its length; a root variable named `length` is an ordinary variable; a FOR item text length.
  - op-equality: `z == "01234"` false for 1234 and true for the text "01234"; `z == "1234"` true for 1234; `"1" == 1` true; `"1.0" == 1` false; unquoted numeric equality unchanged (`1234 == 01234` true, two numeric strings still compare as numbers); `!=` mirrors; `x contains 1.50` finds `1.50` and `007` finds `007`; a quoted right side and a variable right side as before; the same for startsWith and endsWith.
  - op-unknown: `a like b`, `a equals b`, `a matches /x/`, `a == b c`, `a contains b c`, `a isEmpty b`, `a in [x y]`, `a in b in c`, `a in b == c` are located type-errors in all four entries, and `analyze` of the same condition gives an `unrecognized-condition` diagnostic where an operand has bare whitespace. A variable key that contains a space (`"first name"`) used as a whole condition keeps today's behavior (run it to see what that is, and pin it).
  - precedence (one table row each, all four entries): `in`, `not in` and `between` each with AND, OR, NOT, `!` and parentheses, on the left and on the right of the logical word, plus chains such as `a in [1] OR b in [2] AND c` and `NOT (x in [1,2]) AND y between [1,5]`; operator words inside quoted text (`title contains "in the end"`, `x == "a between b"`) never split.
  - op-spec: `spec().operators` contains `in`, `not in`, `between` and `.length` once each and keeps the existing entries in their order; `analyze` variables for `x in ["a", y]`, `x in list`, `x between [lo, hi]`, `items.length > 2` (root `items`, path `items.length`), `{{IF a in b AND c.length > 1}}`, and `${{items.length}}` in output; literals are not variables; a FOR item and `@index0` stay excluded; a malformed `x in [1` gives `unrecognized-condition`.
