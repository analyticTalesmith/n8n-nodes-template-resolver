# Brief: test writer for the node count limit card

## Objective and why

Project goal: a deterministic, no-eval template language for prompt assembly, with a headless core and an n8n node as a thin wrapper.
Cycle goal (`language`): authors can shape values, branch, loop, name, declare and reuse prompt fragments in the language itself without leaving the house style or the no-eval core.
Card goal: a template can no longer be made arbitrarily large. `limits.maxNodes` (default 20000) is counted at parse; an oversize template or a very long ELSEIF chain fails with a located `limit-nodes` diagnostic in render, validate and analyze, on the API and the CLI too. Two older defects ride along: a long ELSEIF chain throws an uncoded RangeError, and `analyze()` throws `limit-depth` for nesting beyond 32 although the caller never asked for a depth limit.
Your objective: turn each criterion below into failing table-driven jest tests that fail for the right reason (an assertion, never a missing import), commit them with signature-only stubs, and record red evidence. The tests are the oracle the implementer is held to, so each must break on a plausible wrong implementation.

- Human decisions in chat, 2026-10-14: render-only behavior changes; `resolveTemplate` outputs unchanged; unknown names are errors in every mode (ADR 0003).
- What counts as a node (settled here so tests and code agree): every AST node except the Program root, counted in document order, a parent before its children, at the moment the parser starts it, located at that node's opening token line and column. A text run is one node; `${{ x }}` is one node; `{{IF}}` is one node; each `{{ELSEIF}}` is one more node (the branch); an ELSE adds none. Exactly `maxNodes` nodes is fine; the node numbered `maxNodes + 1` raises `limit-nodes`. `maxNodes: 0` rejects any non-empty template and accepts the empty template.
- `limit-nodes` joins the other limit codes: a `LimitError` and a diagnostic with `severity: "error"`, `code: "limit-nodes"`, the located line and column, and a suggestion mentioning `limits.maxNodes`. `validate` reports it as an error diagnostic (`ok: false`); `analyze` throws a `TemplateError` with that code (the API turns it into the analysis diagnostic shape, as it already does for `limit-depth`); `resolveTemplate` throws a `TemplateError` with that code.
- Analyze depth decision: with no caller `maxDepth`, `analyze()` no longer uses 32. It succeeds for ordinary deep nesting (for example 40 and 200 nested IF blocks) and bounds only absurd nesting (for example 1000 nested IF blocks) with a `TemplateError` of code `limit-depth` (never a RangeError). A caller `maxDepth` is still obeyed exactly (`analyze(t, {limits:{maxDepth: 5}})` fails at the 6th nested block). `analyze` and `validate` take `limits.maxNodes` the same way.
- No stack overflow, any mode: with default limits, none of render (lenient and strict), validate, analyze or resolveTemplate may throw a RangeError for a long ELSEIF chain or deep nesting; each ends in a result or a coded `TemplateError`.
- Surfaces: render and `resolveTemplate` options `limits.maxNodes`; API `options.limits.maxNodes` is lowered like the other limits (effective value is the minimum of request and server) and a non-integer or negative value is a 400 `invalid-request`; the server's `maxNodes` is also applied by `POST /v1/validate` and `POST /v1/analyze`; CLI `render --max-nodes <n>` (same parsing as `--max-depth`: not a non-negative integer gives exit code 2); the usage text names `--max-nodes`; the OpenAPI `Limits` schema lists `maxNodes` (integer, minimum 0, in `required`) and `RequestLimits` lists it too; `spec().limits` and `DEFAULT_LIMITS` include `maxNodes: 20000`; `withDefaultLimits` fills it.

## How the work is judged

Cases to cover. Keep the test run fast: build big templates with `.repeat`, not loops, and keep each under a second.
- `ln-limit` (unit): table over the surfaces render lenient, render strict, `validate`, `analyze`, `resolveTemplate`, each with `limits: {maxNodes: N}`. Rows: `${{a}}` repeated N times adjacent on one line is fine and N + 1 fails with `limit-nodes` located at line 1, column `6 * N + 1` (check N = 1, 5 and 20); the same on the second line is located on line 2 with the right column; `{{IF t}}x{{END_IF}}` (two nodes) passes at `maxNodes: 2` and fails at `maxNodes: 1` located at the `x` (column 9); `{{IF t}}a{{ELSEIF t}}b{{END_IF}}` is four nodes, failing at 3 located at the `b`; a FOR body and a TABLE row each count their children; `maxNodes: 0` with the empty template is fine and with `x` fails at 1:1; a limit that is not given means 20000 (a template of 20000 adjacent `${{a}}` renders, 20001 fails with `limit-nodes` at column 120001); the diagnostic has `severity: "error"`, a message and a suggestion naming `limits.maxNodes`; render returns `ok: false` and an empty output and never throws; the diagnostic code and location are identical across render, validate and analyze (compare them). The error comes at parse: a template that would also fail later (a missing variable in strict mode) before the crossing node reports `limit-nodes`, not the missing variable, when the count crossed first. Existing limits still work next to it (`maxDepth` and `maxIterations` rows from the same table keep their own codes). The default-limits tests in `tests/headless/limits.test.ts` must keep passing unchanged.
- `ln-elseif` (unit): `'{{IF t}}a' + '{{ELSEIF t}}b'.repeat(20000) + '{{END_IF}}'` with `t` set gives `limit-nodes` (not a RangeError, and no thrown error from render) in render lenient, render strict, validate, analyze and resolveTemplate (a coded `TemplateError`). A chain of 5000 and one of 8000 branches with a body still render ok with the right output (`b` for the first true branch; make the middle branch the only true one using data, for example a chain on `t == "x"` where only branch 4000 matches) and analyze ok. An empty-body chain `'{{IF t}}' + '{{ELSEIF t}}'.repeat(19000) + '{{END_IF}}'` is under the node limit and must give ok in render, validate and analyze with no RangeError (this one catches an implementation that only fixes the parser and leaves the interpreter and analyzer recursive). A chain ending in `{{ELSE}}` after 3000 branches renders the else text when none match. Deep nesting: 40 nested IF blocks render with `limit-depth` by default in render and resolveTemplate (not RangeError); `'{{IF t}}'.repeat(5000) + 'x' + '{{END_IF}}'.repeat(5000)` gives a coded limit-depth in render, validate and resolveTemplate, and a coded `TemplateError` in analyze. A 30000-variable template gives `limit-nodes` in every mode.
- `ln-analyze` (unit): `analyze` of 40 nested IF blocks and of 200 nested IF blocks (no limits given) returns an analysis (blocks IF count equals the nesting); the same at 1000 nested blocks throws a `TemplateError` with code `limit-depth` (not a RangeError); `analyze(t, {limits:{maxDepth: 5}})` on 6 nested blocks throws `limit-depth` located at the 6th opening tag, on 5 it passes; `analyze(t, {limits:{maxNodes: 3}})` applies the caller's node limit while `maxDepth` stays unset (still no depth failure for 40 nested blocks when maxNodes is large); `validate` of 40 nested blocks is ok; `render` of 40 nested blocks still gives `limit-depth` at the 33rd tag (render keeps the default depth 32).
- `ln-surfaces` (integration): API via `start`/`call`: a server started with `limits: {maxNodes: 10}`: render with `options.limits.maxNodes: 5` and 6 adjacent variables gives 200 with `ok:false` and a `limit-nodes` diagnostic; a request value of 50 is capped at 10 (11 variables fail, 10 pass); a request without it uses the server's 10; `options.limits.maxNodes` of `-1`, `1.5` and `"3"` each give 400 `invalid-request` mentioning `maxNodes`; `POST /v1/validate` with 11 variables returns `ok: false` with a `limit-nodes` error diagnostic; `POST /v1/analyze` with 11 variables returns 200 with the analysis diagnostic shape `{code:"limit-nodes", message, line, column}` and empty variables, filters and blocks. CLI via `run`: `render --max-nodes 3` with a 4-variable template file exits 1 and writes `file:1:19: error limit-nodes:` style output on stderr (check the code, line and column, not the message text); `--max-nodes 4` exits 0; `--max-nodes abc`, `--max-nodes -1` and `--max-nodes 1.5` exit 2 with a message naming `--max-nodes`; `--json` output carries the diagnostic; the usage text printed for `--help` names `--max-nodes`; `analyze` of a 40-deep nested template through the CLI exits 0.
