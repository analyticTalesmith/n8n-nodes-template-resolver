# Fix requests, review round 1 (macros card)

Base for "old behaviour": the commit `5ddf88c` (the cycle branch before the macros code). Export it with `git archive 5ddf88c | tar -x -C <scratch dir>` and link `node_modules` there, or probe through a throwaway test outside `tests/`; never edit the worktree's `core/` to probe.

## f1 (defect): a DEFINE that is not at the top level of the template must be a syntax-error at the DEFINE

Failing scenario: `render("{{ROW}}{{DEFINE a()}}x{{END_DEFINE}}{{END_ROW}}", {})` returns ok with empty output (expected: `syntax-error` located at the DEFINE, line 1 column 8); with a `{{CALL a()}}` after it the error is "Unknown macro" at the CALL, and `analyze` lists the macro `a` and counts `blocks.DEFINE` although render does not know it. Same for `{{HEADER}}` at the top level (a ROW or HEADER written at the top level is parsed without `nested`, so `depth` stays 0).
Cause: `parseDefine` rejects only when `this.depth > 0`, and `topLevelDefines` reads only the program body.
Smallest change: a DEFINE is accepted only when it is a direct child of the program body: dispatch DEFINE from the top-level loop of `parse()` only and make every other path (`parseNode` reached from any body, ROW and HEADER cells, LIST_ITEM content, a DEFINE body) report the same located `syntax-error` as today's top-level error. The result for every container must be the same error at the DEFINE in `render`, `resolveTemplate`, `validate` (error) and `analyze` (thrown), in every mode.
Tests: a new `describe("mc-define: ...")` block with rows for ROW and HEADER at the top level, a ROW inside a TABLE, a HEADER inside a TABLE, with and without a later CALL, all four entries plus validate and analyze, expecting `syntax-error` at the DEFINE (not "Unknown macro") and `analyze` never listing it. Also a row that a top-level DEFINE after a top-level TABLE and between text still works.

## f2 (defect): the running output check must not count text that a trimming body can still drop

Failing scenarios (all valid and ok before the card; they now fail with `limit-output`): with `v = "x" + "\n".repeat(30)` and `maxOutputChars: 20`, `{{SECTION "T"}}${{v}}{{END_SECTION}}` renders `"## T\n\nx\n"` (8 chars) at base; with `v = " ".repeat(30)` the SECTION is omitted (empty output; with `skip_empty=true` too); `{{LIST}}{{LIST_ITEM}}${{v}}{{END_LIST_ITEM}}{{END_LIST}}` with `v = "x" + " ".repeat(30)` renders `1. x`. The same through an IF, CASE or FOR inside the SECTION or LIST_ITEM (`{{SECTION "T"}}{{IF true}}${{v}}{{END_IF}}{{END_SECTION}}`) and in a table cell (a cell is trimmed).
Cause: `renderChildren` adds every child's full length to `held` before SECTION strips blank lines, before LIST_ITEM `.trim()` and before a cell is trimmed.
Smallest change (decided design; adjust only if the tests are not met): inside the dynamic extent of a trimming body (SECTION body, LIST_ITEM content, a table cell), outside macro bodies, a non-CALL child adds to `held` only the length of its output with leading and trailing whitespace removed (the sum of these never exceeds the length of the final trimmed text, so no valid old template can fail); a CALL child adds its full length (a macro body starts a fresh non-trimming context, so growth through calls is still bounded inside bodies). To keep whitespace that comes back from CALLs inside a nested IF, CASE or FOR bounded too, also add the whitespace of CALL outputs that sat inside that child (keep one running total of "call output minus its trimmed length" and take the difference around the child). A template with no CALL must behave exactly as at base.
Tests: guard rows (they must pass at base AND after) for the three scenarios above, each also nested in an IF, a CASE clause, a FOR with one item, a table cell, in `render` and `resolveTemplate`; the whitespace-only SECTION and the `skip_empty` one; a boundary pair (a trimmed body exactly at the limit renders, one more character fails). New-feature rows (fail now, pass after): a macro returning 30 trailing newlines called from a SECTION with limit 20 and a valid final output of a few chars renders or fails exactly as the final output + call output rule says (pin: the CALL's full output counts, so this one fails with `limit-output` at the CALL); 100 calls of a macro returning 100 spaces inside a SECTION (and inside an IF inside a SECTION) with `maxOutputChars: 1000` end in `limit-output` with `stats.iterations` at most 22.

## f3 (goal-risk): finished LIST item lines and TABLE cells and rows must count into `held` as they finish

Failing scenario: `{{DEFINE a()}}` + `x`.repeat(100) + `{{END_DEFINE}}{{IF t}}{{LIST}}` + `{{LIST_ITEM}}{{CALL a()}}{{END_LIST_ITEM}}`.repeat(100) + `{{END_LIST}}{{END_IF}}`, data `{t: true}`, `maxOutputChars: 1000`: `limit-output`, but `stats.iterations` is 100 (every call ran); expected at most about 22. The same with `{{TABLE}}{{ROW}}` + `{{CALL a()}}|`.repeat(100) + `{{END_ROW}}{{END_TABLE}}`, with HEADER cells, with `{{FOR}}`-built items and rows, and with many CALLs inside one cell.
Cause: `collectListItems` pushes finished lines into a local array, and `processCellsArray`/`collectRows` build cell strings, outside `held`; only each item's content or each macro body is checked.
Smallest change: add each finished LIST line, and each finished cell (after its trim and pipe escape), to `held` as it finishes and check the limit, locating `limit-output` at the item, ROW or cell node that tipped it; release it when the LIST or TABLE returns (save `held` before and restore it in a `finally`, as the other bodies do). Run the nodes of a cell through the same child loop as other bodies so many CALLs inside one cell are counted as they finish (a cell is a trimming context, see f2). Loops keep their own check and position (`runLoop`, FOR located at the FOR node) exactly as today.
Also: a `RangeError` that is not a stack overflow (message "Invalid string length", a string grown past the engine maximum) must be a `limit-output` diagnostic ("Output is longer than the engine can hold", located 1:1 when no node is known) in `render`, never `limit-depth`; only a stack overflow ("Maximum call stack size exceeded") is `limit-depth`. `analyze` and `validate` keep the stack-overflow rule.
Tests: LIST items, nested LIST, FOR-built items, TABLE rows, HEADER, FOR-built rows, legacy text-row FOR in a TABLE, many CALLs in one cell: 100 calls of a 100-char macro with `maxOutputChars: 1000` give `limit-output` and `stats.iterations <= 22`, in an IF body and at top level; exactly-at-the-limit renders; a growth past the engine maximum: with `limits: { maxOutputChars: Number.MAX_SAFE_INTEGER }` and a chain of macros where each level calls the one below twice over a leaf with a ~1,000,000-character literal text (11 levels), `render` ends with code `limit-output`, not `limit-depth` and never a thrown RangeError (check the strings really overflow on this machine; the chain stays under the default `maxIterations` and `maxDepth`; if the cons-string join does not overflow, build the text with `| json`-style filters or a bigger chain).
