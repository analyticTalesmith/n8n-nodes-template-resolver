## How the work is judged

The frozen criteria (verbatim) each need several table-driven rows that fail today for the right reason and would pass with a correct implementation:

- mc-define: hoisted: a CALL before the DEFINE works; the DEFINE renders nothing; a DEFINE inside any block is a `syntax-error` at it; a name defined twice is a `syntax-error` at the second; a duplicate or invalid parameter is a `syntax-error`.
- mc-call: positional arguments bind to parameters; paths and literals both work; a missing path argument is `missing-variable` at the CALL in strict mode and `null` in lenient mode.
- mc-link: an unknown macro or a wrong argument count is a `syntax-error` at the CALL in every mode, found before output and even in a branch that never renders; in `validate` and `analyze` an unknown name is a diagnostic that `validate` reports as `analysis-warning` (partials may supply it at render, L5), while a wrong count for a known name is thrown like a parse error by `analyze` and is an error in `validate`.
- mc-scope: the body cannot read the caller's SET locals, loop names or `@` metadata; a name in the body that is not a parameter reads the data; parameters shadow data; SET inside the body is local to the body and a call, and a SET of a parameter name is a `syntax-error`; the caller's scope is intact afterwards.
- mc-depth: one runtime depth counter rises on every block entered and every CALL, and is bounded by `maxDepth` and, when a caller raises `maxDepth`, by an internal cap of 256: an infinite recursion, and 32 chained calls each with a body nested 31 blocks deep, at default limits, and recursion through a nested-block body at a raised `maxDepth`, give a located `limit-depth` (or succeed), never a RangeError and never a `type-error`; `render`, `validate` and `analyze` turn a stray RangeError into a `limit-depth` diagnostic instead of rethrowing it or letting `locateError` retype it.
- mc-iterations: every CALL counts one toward `maxIterations`: a fan-out of two per level over 14 levels ends in `limit-iterations`; the count appears in `stats.iterations`.
- mc-output: `maxOutputChars` is enforced across and inside macro bodies and `IF`/`CASE` bodies under a CALL: a macro whose body is larger than the limit divided by the call count, called from an IF body, ends in `limit-output` before the work holds much more than twice the limit.
- mc-locate: an error raised inside a body is located at the failing body node and its message names the macro and the CALL's line and column; it is never moved to the CALL.
- mc-names: macro names `__proto__`, `constructor`, `toString` and `hasOwnProperty` define and call like any name, and an unknown one is "unknown macro", never an inherited member.
- mc-ws: DEFINE and END_DEFINE join the standalone set; CALL does not; trim markers work on all three.
- mc-analyze: analyze and validate walk each DEFINE body exactly once and never follow a CALL (linear cost on fan-out and mutual recursion; rows run through `validate` and `analyze`, not only `render`); parameters are locals in the body; CALL argument paths are usage kind `call`; `blocks` counts DEFINE; unresolved names are warnings in validate; analyze lists the macros it saw in an optional `macros` field present only when DEFINEs exist.
- mc-spec: `spec().blocks` lists DEFINE (closes END_DEFINE) and CALL (no closes); the derived surfaces test passes without edits.
- mc-compat: the full suite passes; no existing test file changes.
